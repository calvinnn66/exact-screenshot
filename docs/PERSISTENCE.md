# KitchenIntel — Persistence Architecture

_Added: 2026-06-13 · Branch: `clawbot-dev`_

---

## Overview

Project data (inventory, recipes, stations, vendors, locations) is stored in
**Supabase as the primary source of truth**, with `localStorage` kept as a
write-through cache for offline access and fast startup.

---

## Database tables

| Table | Purpose |
|---|---|
| `public.projects` | One row per restaurant workspace. Owned by `auth.users.id`. |
| `public.project_state` | Serialized `Persist` JSONB blob for each project. 1:1 with `projects` via FK. |

Both tables use **Row Level Security** with an `auth.uid()` policy, so the
browser anon key is sufficient — no `SUPABASE_SERVICE_ROLE_KEY` is required
for project CRUD. Access is scoped to the authenticated user automatically.

Migration: `supabase/migrations/20260613120000_add_projects_persistence.sql`

---

## Project IDs

All projects created after this migration use **`crypto.randomUUID()`** (real
UUIDs). This enables proper FK references from `toast_connections`,
`square_connections`, and `pos_orders` in Step 3 of the Toast prerequisites.

Pre-migration projects had `prj_abc1234`-style IDs (generated by
`Math.random()`). These are migrated to real UUIDs during the one-time import
(see below).

---

## Load flow (`loadProjects`)

Called once on mount after the user is authenticated.

```
1. Read localStorage (readLocalStore) as the immediate fallback value.

2. Try fetchUserProjects() from Supabase:
   a. If Supabase returns rows → use them as source of truth.
      Update localStorage cache. Return.
   b. If Supabase returns empty AND localStorage has projects →
      One-time import (see below). Return.
   c. If Supabase throws (offline / key absent) → return localStorage value.

3. If both are empty → return empty store (new user, onboarding flow).
```

`lastSyncedProjectsRef` is seeded with the loaded projects immediately after
`loadProjects` returns, so the write-through effect does not fire a spurious
upsert on the initial render.

---

## One-time localStorage → Supabase import

Runs automatically the first time an existing user logs in after this
migration is deployed.

```
1. Generate new crypto.randomUUID() for each project.
2. Build an old-ID → new-ID map.
3. Await Promise.all(upsertProject(...)) for every project.
4. Only if ALL upserts succeed: write the new-UUID store to localStorage.
5. If any upsert fails: fall back to localStorage as-is (retry next login).
```

The import is safe to retry: if it partially succeeds on one login, the next
load finds Supabase has some projects and uses them as the source of truth
(step 2a above).

---

## Write-through (`saveProjects` + Supabase sync)

Every store change (inventory edit, station rename, item delete, etc.) triggers
a two-step write:

1. **Synchronous localStorage write** — zero latency, always runs first.
2. **Debounced Supabase upsert** (800 ms after the last change):
   - Diffs `store.projects` against `lastSyncedProjectsRef.current`.
   - Calls `upsertProject` only for new or changed projects.
   - Calls `deleteProjectFromDb` for any projects removed from the store.
   - Errors are swallowed — local state is always current; Supabase is
     eventually consistent.

The 800 ms debounce batches rapid successive changes (e.g., multiple inventory
adjustments) into a single Supabase round-trip.

## Client module

`src/lib/projects-db.ts` — browser Supabase client, no server function needed.

| Export | Description |
|---|---|
| `fetchUserProjects()` | SELECT projects + project_state for current user |
| `upsertProject(id, userId, name, type, state)` | Idempotent two-step upsert |
| `deleteProjectFromDb(id)` | Delete project row (cascades to state) |

The file is named `projects-db.ts` (not `projects.client.ts`) to avoid
TanStack Start's `*.client.*` import-protection rule, which blocks `.client.*`
files from being imported by SSR routes.

## Persist type — current shape

```typescript
type Persist = {
  brand: string;
  locations: Location[];
  activeLocationId: string | null;
  stationModules: StationModule[];
  categories: string[];
  vendors: Vendor[];
  items: Item[];        // usage: number[7] updated by real POS feed tick
  menu: MenuItem[];
  sales: SalesRow[];    // added P0-1 (2026-06-16); capped at 500 rows in write-through
};
```

`sales` is restored from `init.sales ?? []` on project load. The write-through
uses `sales.slice(0, 500)` to prevent the `project_state` JSON blob from growing
unbounded. In-memory the runtime cap is 200 rows (per `setSales` calls).

## Known limitations

- `toast_connections`, `square_connections`, and `pos_orders` still use
  `project_id TEXT` referencing pre-migration `prj_abc1234`-style IDs. These
  columns will be migrated to UUID FK references (roadmap P2-A).
- No conflict resolution — last write wins. Concurrent edits from two browsers
  logged in as the same user will overwrite each other (roadmap P2-C).
